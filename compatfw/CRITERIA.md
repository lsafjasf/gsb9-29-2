# 兼容性判定标准（通过判据说明）

每个“生产者（某版本写入器）× 读取方（某版本读取器）”组合，只允许以下三种
**通过**结论，且每格必须给出依据：

| 结论 | 含义 | 通过条件（全部满足） |
| --- | --- | --- |
| `EQUIV` | 可读且内容等价 | 无异常；返回明文长度与源一致；SHA256 与源一致；读取方原生支持该文件版本，`needs_conversion=False` |
| `CONVERT` | 可读但需转换 | 无异常；长度与 SHA256 一致；但文件版本旧于读取方，读取方报告 `needs_conversion=True`，必须能用新版本重写并再次等价读取 |
| `REJECT` | 明确拒绝并给出原因 | 抛出带 `reason` 原因码的格式异常；**未返回任何部分明文**；原因码与用例期望一致 |

以下结论**一律不通过**：

| 结论 | 触发条件 |
| --- | --- |
| `PARTIAL` | 读取方暴露了部分明文后才报错（异常携带 `partial_plaintext`）。**读到部分内容不算通过** |
| `FAIL` | 解密返回但内容不等价（长度或哈希不一致），或行为/原因码与期望不符（例如期望 `REJECT` 却解密成功） |
| `ERROR` | 抛出非约定异常（如裸 `RuntimeError`），代表读取实现或框架自身缺陷 |
| `NA` | 组合不适用（不计入通过/失败） |

## 关键判定原则

1. **等价比对双重校验**：长度 + SHA256，防止“长度碰巧相同但内容错误”蒙混过关。
2. **拒绝必须 fail-closed 且有原因**：拒绝类用例不仅要求抛异常，还要求 `reason`
   原因码与期望一致（见下表），避免“碰巧抛了个别的错”被判通过。
3. **部分读取永不通过**：即使异常最终抛出，只要部分明文被带出，判 `PARTIAL`。
4. **检查顺序决定拒绝原因**：读取流程为 魔数/版本 → 密钥查找 → 头 HMAC →
   块大小范围 → 逐块（序号/长度/块 HMAC）→ 尾部长度。因此 R1（旧程序）读 v2
   文件时，在版本门即拒绝，原因是 `unsupported_version`，与后续密钥/篡改无关。
5. **CONVERT 必须可执行**：不仅看标记，还要实际完成“旧文件 → 新程序读出 →
   新版本重写 → 再读等价”的完整往返（转换路径检查）。

## 拒绝原因码表

| reason | 含义 |
| --- | --- |
| `unsupported_version` | 读取方不支持文件格式版本（旧程序读新文件） |
| `key_not_found` | 密钥环缺少文件头声明的 `key_version` |
| `unsupported_block_size` | 声明块大小超出读取方支持范围 |
| `header_mac_mismatch` | 文件头 HMAC 校验失败（头被篡改或密钥不匹配） |
| `block_mac_mismatch` | 数据块 HMAC 校验失败（块被篡改或密钥不匹配） |
| `truncated` | 文件/块截断，声明的块未完整出现 |
| `trailing_data` | 声明块之后存在多余字节 |
| `block_index_mismatch` | 块序号不连续 |
| `block_too_large` | 块长度超过声明的块大小（如块大小声明被改小） |
| `bad_magic` / `unknown_version` | 非本格式文件 / 未知版本号 |

判定逻辑实现见 `compat/harness.py` 的 `run_case`，原因码中文解释见
`compat/verdicts.py` 的 `REJECT_REASONS`。
